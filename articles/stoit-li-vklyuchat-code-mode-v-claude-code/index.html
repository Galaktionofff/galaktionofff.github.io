Стоит ли включать Code Mode в Claude Code ради экономии?

Проверка битых ссылок заняла три минуты вместо 27 секунд. Это не опечатка: в экспериментальном Code Mode агент сэкономил входные токены, но написал больше сотни мелких команд и проиграл обычному режиму по времени. Если платишь не только деньгами, но и ожиданием результата, одной цифры экономии мало.

Я бы включал режим не для любого запроса, а для длинной работы с множеством файлов. И сначала проверил бы, какой именно ресурс он экономит.

Code Mode позволяет агенту собрать несколько обращений к инструментам внутри одного фрагмента кода.

Что меняется под капотом

В обычной сессии Claude Code читает файл, получает ответ, выбирает следующий инструмент и снова передаёт модели историю работы. В документации Anthropic Code Mode описан иначе: модель пишет JavaScript, который вызывает инструменты, использует промежуточные результаты и возвращает ей только нужный фрагмент. Ты по-прежнему пишешь задачу обычным языком. Режим относится к способу вызова инструментов, а не к отдельной модели для программирования.

При поиске в десятках файлов модель может получить короткий список путей вместо длинной россыпи результатов. Код исполняется в твоей сессии, а действия агента можно изучить через Ctrl+O.

Где исчезают токены, а где — время

Автор практического разбора Nate Herk сравнил режимы на четырёх небольших заданиях: обработка 40 файлов заказов, поиск битых ссылок в 30 документах, правка сайта из 25 страниц и вопрос по одному файлу. Задачу с заказами он повторил, поэтому в сравнении пять пар запусков. По его словам, ответы оказались правильными в обоих режимах; это не независимый бенчмарк и не гарантия для другого проекта.

В его конфигурации Code Mode израсходовал примерно на 35% меньше входных токенов. Однако значительная часть этого выигрыша пришлась на системные инструкции и список инструментов: около 60 тысяч токенов на сообщение в обычном режиме против 38 тысяч с одним инструментом для кода. Многие такие токены кэшируются и стоят дешевле нового ввода. Автор оценил экономию с учётом кэша примерно в 17%, а не в 35%. Это его расчёт, не обещание уменьшить счёт каждому.

Сокращение входного объёма нельзя напрямую выдавать за такую же экономию денег.

По скорости результат оказался смешанным: в трёх заданиях Code Mode был медленнее, в быстром вопросе и одном повторе обработки заказов — быстрее. Проверка ссылок особенно показательна: вместо одной команды агент запустил больше сотни отдельных команд оболочки. На Windows запуск каждой добавлял задержку. А в обычном режиме модель и без новой функции иногда сама пишет скрипт и запускает его терминалом. Поэтому сравнивать нужно завершённую задачу, а не красоту схемы «много вызовов превратились в один».

Как попробовать, не ломая рабочую сессию

По текущим требованиям Anthropic нужен нативный Claude Code версии не ниже 2.1.323, совместимая модель и интерактивная терминальная сессия. Экспериментальная функция выключена по умолчанию. В bash её запускают так: CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1 claude; при первом старте подтверждают включение. Настройка в пользовательском ~/.claude/settings.json тоже поддерживается, но проектный файл настроек не должен включать режим за тебя.

На копии проекта дай проверяемую задачу: собрать список ссылок и отдельно проверить его скриптом. Зафиксируй версию клиента, модель, запрос и состояние файлов. Проведи несколько пар запусков: сравни итог, время, токены с разбиением на кэш и число команд. Один прогон мало что доказывает: у Herk даже обычный режим заметно менялся по времени.

Не включай настройку вслепую в рабочем процессе с браузером: документация предупреждает о несовместимости Code Mode с Claude in Chrome, computer use и переносом сессии в Desktop. Возобновить сессию, созданную в этом режиме, можно лишь с включённым режимом. Функция экспериментальная; требования и поведение могут измениться после обновления.

Когда я бы оставил переключатель выключенным

Мне Code Mode интересен для поиска и фильтрации по большому набору файлов, когда поток сырых результатов забивает контекст. Но одиночный вопрос по файлу или короткая правка не заслуживают смены режима только ради обещанной экономии. В собственных автоматизациях на Hermes и n8n я сначала смотрю на итоговый артефакт и время до него; оптимизация токенов идёт следом.

Если агент дробит простую работу на десятки запусков оболочки, я бы вернулся к обычному режиму или задал ему более конкретный способ проверки. Что для вас дороже в такой задаче: лимит токенов, минуты ожидания или необходимость потом перепроверять действия агента?
