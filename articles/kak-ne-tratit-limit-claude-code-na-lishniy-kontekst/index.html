Как перестать тратить лимит Claude Code на старые задачи?

Ты исправил баг, перешёл к письму клиенту, а потом попросил агента набросать тесты. Во всех трёх случаях он получил историю предыдущих разговоров. Даже когда повторный ввод обслуживает кэш, длинный чат остаётся длинным: за ненужный контекст всё равно платят токенами или расходуют лимит подписки.

Я взял за отправную точку разбор Нейта Херка о привычках пользователей Claude Code, но проверил советы по документации Anthropic. Там есть существенная оговорка: цена API-запроса и полоска недельного лимита подписки — разные вещи. Точную экономию в часах или процентах здесь никто не гарантирует.

Старые задачи продолжают занимать контекст, пока ты не начнёшь новую сессию.

Сначала посмотри, что расходуется

В Claude Code команда /usage показывает расход сессии по вводу, выводу, чтению и записи кэша. Для API-пользователя оценка в долларах считается по токенам; для подписчика это не счёт к оплате, а отдельные показатели плана. Если команда показывает много cache read, это не означает нулевой расход: кэшированный ввод дешевле обычного, но не бесплатен.

Документация Anthropic о кэшировании описывает три слоя: системные инструкции и инструменты, контекст проекта, затем историю беседы. Кэш повторно использует совпадающий префикс. Когда меняются определения инструментов или прежние сообщения, часть истории приходится обработать заново. Но из этого не следует, что любой переход на дешёвую модель непременно дороже: результат зависит от длины истории, тарифа модели и дальнейшего числа запросов. В ролике Херка это скорее предупреждение о скрытой цене переключения, а не универсальная формула.

Раздели работу по задачам

Самый полезный приём для меня — завершать задачу отдельной сессией. /clear открывает чистую историю; когда нужно сохранить результаты, сначала записываю важное в файл проекта либо делаю краткую передачу контекста. Если задача продолжается и история уже разрослась, /compact делает резюме вместо полного чата. Это не бесплатная кнопка: сжатие само читает историю и пересобирает кэш.

Вместо «найди ошибку во всём репозитории» дай агенту точку входа: файл, функцию, ожидаемое поведение и команду проверки. Меньше случайно открытых файлов — меньше шума в ответе. Но не запрещай поиск совсем: если названный файл не объясняет сбой, агенту нужны соседние модули и тесты. Я предпочитаю разрешить расширить область после первой проверяемой гипотезы, а не заставлять его угадывать по одному фрагменту.

Новая задача не обязана тащить за собой переписку о предыдущей.

Убери постоянный груз из инструкций

CLAUDE.md загружается как проектный контекст. Если туда складывать каждый временный рецепт, агент будет видеть лишние правила в неподходящих задачах. Руководство Claude Code советует держать файл коротким, ориентир — менее 200 строк на файл. Это рекомендация по управляемости, а не жёсткий предел продукта. Разовые процедуры разумнее вынести в навыки, которые открываются по необходимости; неизменные ограничения проекта оставить на виду.

Я бы начал с ревизии противоречий: одна строка требует писать комментарии, другая запрещает их. Такую пару нельзя «оптимизировать» одной лишь сменой модели. Потом проверил бы, какие инструкции действительно нужны каждому запросу. Удалять все правила разом опасно: сначала сохрани контрольный набор задач, прогони до и после и сравни не только длину контекста, но и качество результата.

Кэш живёт ограниченное время: стандартное время жизни в API — пять минут с обновлением при использовании; у Claude Code с подпиской обычно около часа. Не советую отправлять пустые запросы ради его «подогрева»: новый запрос тоже расходует ресурсы, а выигрыш зависит от конкретной сессии. Мой выбор проще: проверить /usage, разделить несвязанные задачи и не держать лишние инструкции постоянно загруженными.

Где у тебя чаще уходит лимит: на длинный чат с несколькими задачами, на чтение всего проекта или на постоянно разрастающийся CLAUDE.md?
