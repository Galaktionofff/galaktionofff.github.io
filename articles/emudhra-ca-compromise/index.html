Ключи от интернета утекли: почему прямо сейчас нужно обновить certifi, pip и серверы

Многие привыкли: если запрос идёт по HTTPS, трафик защищён. Замок горит, код не ругается — значит, соединение безопасно. Мы передаём токены API, качаем пакеты и верим серверам на том конце.

20 октября 2026 года в этой уверенности появилась дыра. Скомпрометированы приватные ключи сразу 8 промежуточных удостоверяющих центров eMudhra. Это напрямую касается каждого, кто пишет код или держит серверы.

Компрометация промежуточных ключей eMudhra позволяет создавать валидные SSL-сертификаты для любых доменов.

Анатомия инцидента: как ломается цепочка доверия

Начнём с базы: софт проверяет подлинность сайтов по цепочке. Корневой центр (Root CA) не подписывает домены напрямую: это рискованно. Он выпускает промежуточные сертификаты (Intermediate CA), наделяя их правом подписи.

Простым языком: если корневой центр — это госведомство, то промежуточный центр — нотариус с печатью. Клиент верит нотариусу, потому что за него поручилось государство.

Именно нотариальные ключи eMudhra и утекли. Восемь центров цепляются к корневым программам Mozilla, Microsoft, Apple и Chrome, а через них — к десяткам хранилищ софта.

То есть ещё раз: злоумышленник с этими ключами может выпустить валидный SSL-сертификат для любого домена. Ни браузер, ни скрипт не заметят подвоха — это готовый инструмент для перехвата данных и атак «человек посередине». Контекст события и выводы — в Telegram.

Ловушка встроенных хранилищ: ОС обновилась, а софт — нет

Операционные системы отреагировали быстро: вендоры выкатили списки отзыва. Но в реале расклад такой: апдейт ОС защищает только системный браузер.

Многие среды не смотрят в сертификаты ОС, а хранят trust store внутри пакетов. Старый Docker-контейнер или серверное окружение не знают о блокировках системы и продолжают доверять ключам eMudhra.

В дистрибутивах Linux уже вышли патчи пакетов ca-certificates. Следом обновился Python-инструментарий: * uv обновился до 0.13.4; * pip получил релиз 26.2.2; * certifi вышел в версии 2026.10.19.

Детали инцидента разобрал в блоге Саймон Уиллисон, а сообщество мониторит обновления в репозитории проекта-монитора. Связанные материалы и разборы — здесь.

Инструменты со встроенным списком сертификатов остаются уязвимыми до ручного обновления пакетов.

Почему это бьёт по автономным агентам и пайплайнам

Для тех, кто гоняет сетевые пайплайны и агентные связки, это отрезвляющий сигнал.

Агенты непрерывно делают сотни HTTPS-запросов: обращаются к API моделей, тянут страницы и качают зависимости. Чаще всего этот софт крутится в контейнерах, которые годами не обновляются.

Особо никакой магии нет: если запрос идёт из окружения со старым certifi через скомпрометированный узел, трафик можно расшифровать и подменить без алертов в логах. Токены API и промпты оказываются открыты для перехвата.

Доверие по цепочке — хрупкая штука. Безопасность упирается не в абстрактную математику, а в надёжность чужих регламентов. Об этом событии я разбираю подробнее — в канале.

Безопасность инфраструктуры требует накатки свежих версий пакетных менеджеров и пересборки контейнеров.

Что сделать прямо сегодня: чеклист для серверов и CI

Логика простая — навести порядок на ключевых уровнях:

  1. Обновите Python-окружения: pip install -U pip certifi или обновите uv до 0.13.4. Убедитесь, что активен certifi>=2026.10.19.
  2. Обновите сертификаты на серверах: в Ubuntu/Debian выполните sudo apt update && sudo apt install --only-upgrade ca-certificates.
  3. Пересоберите Docker-образы и CI: сбросьте кэш сборок, чтобы не тащить устаревшие бандлы сертификатов.
  4. Сверяйтесь с монитором: проверяйте репозиторий проекта, если используете другие стеки со своими хранилищами.
