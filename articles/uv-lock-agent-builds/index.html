Агент застрял на сборке Python? Не спеши удалять uv.lock

Совет «сборка сломалась — удали uv.lock» опасно похож на лечение компьютера переустановкой системы. Иногда помогает. Только причину ты так и не узнал, а зависимости уже другие.

Я сверил этот рецепт с документацией uv, менеджера Python-проектов. Меня зацепила ошибка в самом объяснении: lock-файл называют слепком чужой машины. У uv он устроен иначе. Для агента, который чинит сборку по кругу, эта разница важнее очередного промта «подумай лучше».

Ошибка сборки ещё не доказывает, что нужно выбрасывать зафиксированные зависимости.

Lock-файл не привязан к одному ноутбуку

В документации Astral uv.lock описан как универсальный, кроссплатформенный файл. Он хранит разрешённые версии зависимостей с учётом условий: версии Python, операционной системы, архитектуры. Это не копия установленной папки .venv.

Поэтому переход с Windows на macOS сам по себе не делает lock «мусором». И смена Python не означает гарантированную поломку. Другое дело — конкретный пакет: для нового интерпретатора может не оказаться подходящей готовой сборки, wheel. Тогда установка может перейти к сборке из исходников, а ей потребуются компилятор и системные библиотеки.

Есть три разных объекта: требования в pyproject.toml, выбранные версии в uv.lock и установленное окружение .venv. Ещё отдельно живёт кэш скачанных и собранных пакетов. Когда агент смешивает всё это в одну «проблему зависимостей», он способен чинить не тот слой сколько угодно.

Сначала выясни, что именно сломалось

Иногда самая дешёвая оптимизация — открыть документацию. В правилах синхронизации uv уже есть средства, которые полезнее автоматического удаления файла.

Первый шаг — сохранить исходную ошибку и определить этап. Не удалось скачать пакет? Не нашёлся совместимый wheel? Упал компилятор? Проект запущен другим Python? Одинаковая просьба «почини установку» скрывает разные задачи.

Второй — проверить согласованность требований и фиксации: uv lock --check. Команда завершается ошибкой, если lock требует обновления. Для установки без его изменения есть uv sync --locked: устаревший файл даст ошибку вместо незаметного пересчёта.

Третий — менять только то, на что указывает лог. Пример формы команды: uv lock --upgrade-package имя-пакета. Вместо «имя-пакета» ставится реальная зависимость из ошибки. Обновление ограничено требованиями проекта; если нужна новая версия вне этих границ, сначала придётся осознанно изменить требования.

Разборы таких ограничений я продолжаю в канале об ИИ и автоматизации: здесь интересен не героизм агента, а цена его решений.

Три слоя проекта и отдельный кэш требуют разных способов исправления.

Кэш чистят отдельно от фиксации версий

Если подозрение именно на кэш, у uv есть uv sync --refresh-package имя-пакета: перепроверка данных для выбранной зависимости. Есть и адресная очистка uv cache clean имя-пакета. В документации по кэшу это отдельные операции, а не повод заново выбирать весь набор версий.

Удаление uv.lock меняет другую вещь: при следующем разрешении зависимостей исчезает опора на прежние зафиксированные версии. Новый набор может пройти тесты, но это уже обновление зависимостей, а не доказательство порчи старого файла. Сравни изменения через Git и прогони тесты до принятия такого «ремонта».

Я бы не зашивал удаление lock в автоматическое правило для Hermes или Antigravity. Агент должен сначала объяснить, почему текущая версия пакета несовместима, и показать минимальную правку. Иначе зелёная установка маскирует десяток незапрошенных обновлений.

Правило остановки полезнее правила удаления

Практический предел я предлагаю такой: после двух одинаковых ошибок без новой гипотезы остановить повторные запуски. Это не статистика uv и не измеренный выигрыш, а ограничитель для автоматизации. Дальше нужен отчёт: пакет, интерпретатор, команда, первая существенная ошибка и следующее проверяемое предположение.

В экспериментальной ветке пересоздать lock допустимо. В рабочем проекте я считаю более разумным сохранить исходное состояние, проверить совместимость и отдельно согласовать обновления. Воспроизводимость не обещает, что сборка никогда не упадёт. Она позволяет понять, что именно ты изменил, когда сборка наконец прошла.
