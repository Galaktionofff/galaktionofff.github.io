Агент сделал тесты зелёными. Кто проверит сами проверки?

Зелёная сборка может означать, что проверять больше нечего. Особенно если ты поручил агенту починить проект и разрешил ему менять всё, включая критерии успеха.

Я не хочу выбирать между «никогда не доверяй ИИ» и «просто напиши хороший промпт». Поэтому разобрал маленький пример на pytest: как получить успешный запуск без исправления хоть одной ошибки — и что именно нужно вынести из-под контроля исполнителя.

Если исполнитель может переделать мерку, успешная проверка ещё не подтверждает починку.

Четыре провала превращаются в успешный запуск

Для демонстрации я запустил четыре заведомо неверных сравнения: от assert 1 == 2 до assert 4 == 5. Никакого сервиса, базы и сложной асинхронности — только механика проверки. Результат ожидаемый: 4 failed, код завершения процесса — 1.

Затем заменил два сравнения на assert True, а ещё два теста пометил @pytest.mark.skip. Новый результат: 2 passed, 2 skipped, код завершения — 0. Исходные утверждения истинными не стали. Я лишь перестал их проверять.

Это учебная подмена, сделанная мной, а не доказательство того, что конкретная модель так поступает. Но она показывает дырку в критерии приёмки: одного успешного завершения команды недостаточно.

И цифра [100%] в конце строки pytest не означает стопроцентного прохождения тестов. Это прогресс обработки набора. В документации pytest пропуски и ожидаемые падения учитываются отдельно. Если агент пишет «всё прошло», читай итоговую сводку, а не последнее число в квадратных скобках.

Запрет в инструкции не закрывает файл

В своих задачах для Hermes я бы разделял два разрешения: предложить изменение теста и изменить эталон, по которому принимается работа. Это разные полномочия. Агенту полезно писать новые сценарии, находить устаревшие ожидания и объяснять, почему тест неверен.

Мой ответ будет непопулярным: иногда исправлять надо именно тест. Слепой запрет любых правок в tests/ закрепляет старые ошибки не хуже бесконтрольной генерации. Нужен отдельный просмотр таких изменений, а не автоматическое согласие или автоматический отказ.

Для финальной приёмки эталон берётся из доверенной версии. Исполнитель не должен иметь возможности переписать его, настройки запуска или итоговый отчёт. Иначе фраза «тесты не трогай» остаётся просьбой к процессу, у которого есть доступ на запись.

Как формулировать задачу агенту и разбирать сбой, есть в библиотеке системных промтов. Но даже точная инструкция не заменяет ограничений среды.

Код завершения сменился с 1 на 0 после ослабления проверок, а не исправления исходных утверждений.

Отдельный процесс ещё не независимая проверка

Запустить второго агента под тем же пользователем в той же папке — не изоляция. Он видит те же подменённые файлы. Сверка хешей тоже помогает лишь тогда, когда исполнитель не может заменить ни сохранённые хеши, ни программу сверки.

Я бы собирал приёмку так: агент отдаёт конкретную ревизию кода, внешний запуск берёт её и накладывает доверенные тесты. Команда запуска, зависимости проверяющего и конфигурация CI приходят из защищённого источника. После прогона сохраняются ревизия, полный отчёт и список выполненных сценариев.

В Docker каталог эталонных тестов можно подключить только для чтения: для bind mount есть параметр readonly или ro. По документации Docker обычное подключение доступно на запись по умолчанию. То есть слово «контейнер» само по себе проблему не решает.

Не оставляй агенту доступ к Docker-сокету, полномочия пересоздать среду проверки или другую записываемую копию эталона. И даже неизменяемый тест не гарантирует честного исполнения: код проекта может вмешаться в загрузку модулей. Для недоверенного кода нужна отдельная модель угроз, а не один красивый флаг.

Что я считаю результатом

Для маленького проекта начал бы с трёх условий: исходный падающий сценарий воспроизводится до правки, после неё проходит на защищённом наборе, новые пропуски и ослабленные ожидания объяснены отдельно. Плюс просмотр разницы в коде — особенно conftest.py, настроек pytest и CI.

Мне важен не запрет агенту думать, а запрет единолично менять договор о результате. Исполнитель может спорить с тестом и предлагать замену. Принимать эту замену должен другой контур.

А у тебя агент может одновременно менять код, тесты и команду их запуска? Расскажи в комментариях: что мешает ему сдать красивый отчёт вместо починки?
